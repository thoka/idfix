# How the sandboxed oc-sub server calls DeepInfra while the key stays on the host

Research on 2026-10-01. No paid API call was made, no key file was read, and no `sbx secret` command was run. Context: `oc-sub` runs `opencode serve` inside a Docker Sandbox (`sbx` 0.45.1); the OpenRouter key stays on the host (`sbx secret set openrouter --sandbox NAME --command 'cat <keyfile>'`, src/sandbox.ts:1143–1159) and the host-side proxy of `sbx` injects it into every request to openrouter.ai. The project DeepInfra key lives in `~/.config/opencode-subagents/deepinfra.key`, and `deepinfra` is not in the service list of `sbx secret set`. See also [DEEPINFRA.md](DEEPINFRA.md) (precision and cost measurement), [SANDBOX.md](SANDBOX.md) (the sbx test), [COST_PROXY.md](COST_PROXY.md) (the cost proxy).

## Criteria

From the global rules (research before assumption, quality first, small blast radius) and the brief:

- K1 Key safety: the real DeepInfra key never enters the sandbox (never in env, files, or request bytes visible to the agent).
- K2 Code effort: how much new code in oc-sub a production-quality version needs.
- K3 Cost truth: how exact and how timely oc-sub can learn the real cost of a run.
- K4 Rate limits and overhead: request limits, extra hops, extra fees, and routing surprises.
- K5 Structural fit: the option must not undo the sandbox boundary that src/sandbox.ts:39–46 deliberately builds (deny `host.docker.internal` and all private ranges).

## Short answers

1. **Yes.** `sbx` has two supported paths for hosts outside the built-in service list: the experimental **`sbx secret set-custom`** (a secret keyed to one or more domains plus an environment variable; the proxy replaces the placeholder wherever it appears in the request) and a **custom kit** whose `spec.yaml` declares a service with `apiKey.inject` domains and header. Both keep the real value on the host. Whether both exist in exactly 0.45.1 is unconfirmed (the docs are version-less; the brief forbids running `sbx secret` commands to check).
2. **Yes, OpenRouter BYOK supports DeepInfra.** Add the key in the workspace BYOK settings; requests routed to DeepInfra then bill the DeepInfra account. The fee is **5% of what the same model/provider would cost on OpenRouter**, deducted from OpenRouter credits, waived under a plan-dependent free allowance measured by list-price inference cost ($25,000/month on Pay-as-you-go). BYOK requests bypass OpenRouter's free-model rate gates and use the provider's own limits. BYOK **can** be limited to specific OpenRouter API keys (`allowed_api_key_hashes`), specific models, and specific members. Cost learning: the stream's `usage.cost` still reports what OpenRouter charged (the 5% fee and the DeepInfra charge arrive as one number), and DeepInfra's `GET /payment/usage/{api_token}` gives the raw DeepInfra spend per key.
3. **The sandbox can reach `host.docker.internal` today under the default policy**, but oc-sub's own `up` explicitly denies it (src/sandbox.ts:39–46, 1097–1099), and SANDBOX.md section 7 (problem 4) shows why: an agent inside the sandbox can then reach any host service. A host-side forwarder is therefore possible but structurally wrong — it reopens the hole that src/sandbox.ts closes, and the `sbx` docs treat proxy-managed credentials, not host proxies, as the credential mechanism.
4. **Recommendation: option A, `sbx secret set-custom` (or a small custom kit) targeting `api.deepinfra.com`.** It is the deciding criteria K1, K2, and K5: the key stays on the host by construction, the code effort in oc-sub is one `sbx` invocation plus a placeholder file like the openrouter one today, and it does not reopen the host-reachability hole. BYOK (option B) is the runner-up if `set-custom` is missing in 0.45.1, because it costs only OpenRouter settings and gives exact per-key cost, but it adds the 5% fee above the allowance, one extra provider hop, and a billing surface. The host forwarder (option C) fails K5 and is out.

## 1. Can `sbx` 0.45.1 inject a secret into requests to a host outside its service list?

Yes, three documented mechanisms exist besides the built-in services. Sources: https://docs.docker.com/ai/sandboxes/security/credentials and https://docs.docker.com/ai/sandboxes/configuration/credentials (both fetched 2026-10-01 via web search; quotes from the search result pages):

- **Custom secrets.** "For credentials that don't fit the service-identifier model — for example, when an agent validates the environment variable format at boot, or when the credential lands in a request body rather than a header — use `sbx secret set-custom`. The secret is keyed on one or more target domains, an environment variable name, and an optional placeholder string, instead of a service identifier." And: "Inside the sandbox, `API_KEY` is set to a generated placeholder (for example, `sbx-cs-`). When a sandboxed process sends a request to any of the configured hosts and the placeholder appears anywhere in the request, the proxy replaces it with the real value. The agent never sees the real secret." Custom secrets accept `--sandbox` scoping and dynamic sources (`--ref`, `--command`) like service secrets.
- **Custom kits.** "Custom kits can declare their own service identifiers in `spec.yaml`." The kits page (https://docs.docker.com/ai/sandboxes/customize/kits) shows the full pattern: `network.serviceDomains` tags traffic to a domain, `serviceAuth` names the header and value format (`Authorization`, `Bearer %s`), `credentials.sources` points at a host-side lookup, and `environment.proxyManaged` sets the in-VM env var to `proxy-managed`. "The real secret never enters the VM." Kits v2 (https://docs.docker.com/ai/sandboxes/customize/kits-v2) express the same as a `credentials:` list entry with `apiKey.inject[].domain`, `.header`, and `.format`; every injected domain must also be in `permissions.network.allow`.
- **Credential bindings** (`~/.config/sbx/credentials.yaml`) are only an approval record for third-party v2 kits; built-in-kit credentials inject without a binding.

For DeepInfra the minimal path is `sbx secret set-custom deepinfra --sandbox NAME --command 'cat ~/.config/opencode-subagents/deepinfra.key'` (exact flag names unconfirmed) with `DEEPINFRA_API_KEY` set to the placeholder inside the sandbox — the same shape oc-sub already uses for openrouter (src/sandbox.ts:1143–1170). The placeholder-appears-anywhere rule matters: opencode's `@ai-sdk/deepinfra` sends `Authorization: Bearer <DEEPINFRA_API_KEY>`, so the proxy sees the placeholder in the header and replaces it. If `set-custom` cannot rewrite a header (its docs describe replacing the placeholder anywhere in the request, which covers the header), the kit path with `serviceAuth`/`apiKey.inject` is the fallback.

**Unconfirmed:** whether `sbx secret set-custom` and v2 kits exist in exactly 0.45.1. The docs pages carry no version; the brief forbids running `sbx secret` commands, so the one-command check (`sbx secret set-custom --help`) is left to the main thread. The `sbx-releases` repository was active on 2026-10-01 (`gh api repos/docker/sbx-releases`: pushed 2026-10-01), so the docs likely describe current releases.

## 2. OpenRouter BYOK with the DeepInfra key

All from the OpenRouter docs (fetched 2026-10-01):

- **Mechanism and billing.** "Using provider keys enables direct control over rate limits and costs via your provider account. Your provider keys are securely encrypted and used for all requests routed through the specified provider" (https://openrouter.ai/docs/guides/overview/auth/byok). So requests that OpenRouter routes to DeepInfra use the DeepInfra key and bill the DeepInfra credits. DeepInfra (`deepinfra`) is in the BYOK provider list of the credentials API (https://openrouter.ai/docs/api/api-reference/byok/create-a-byok-provider-credential).
- **Fee and free quota.** "The cost of using custom provider keys on OpenRouter is 5% of what the same model/provider would cost normally on OpenRouter and will be deducted from your OpenRouter credits. The free allowance is plan-dependent and measured by list-price inference cost, not request count: Pay-as-you-go includes $25,000 per month, while Enterprise includes $200,000" (same BYOK page; the FAQ agrees). For oc-sub's volume the allowance is effectively unlimited; the real cost is the fee only if the allowance is ever exceeded. Note the fee is on the *OpenRouter list price* of the model, not on the discounted DeepInfra price.
- **Rate limits.** "When you use OpenRouter credits, your rate limits for each provider are managed by OpenRouter. Using provider keys enables direct control over rate limits and costs via your provider account" (BYOK page). BYOK requests "are not gated by" the free-model daily limits (https://openrouter.ai/docs/api_reference/limits). OpenRouter's global DDoS protection still applies (same page: rate limits govern request counts; "Making additional accounts or API keys will not affect your rate limits, as we govern capacity globally"). DeepInfra's own account limit applies upstream (morphllm.com reports 200 concurrent requests per DeepInfra account — secondary source, unconfirmed).
- **Scoping.** "API key filter, restrict which of your OpenRouter API keys can use this BYOK key. Useful for isolating BYOK usage to specific applications or environments" (BYOK page). Implemented as `allowed_api_key_hashes` on the BYOK credential (management API, same page). Model filters (`allowed_models`) and member filters exist too, plus a per-key "Shared capacity fallback" setting with a strict "Never use shared capacity for any model on this provider" level (`is_byok_only: true`). So BYOK can be pinned to one OpenRouter key and one model — a good isolation boundary. Workspace-scoped, not per-project: the BYOK credential lives in a workspace; OpenRouter has no per-project concept beyond API keys.
- **Cost learning.** Three sources, all existing machinery:
  1. The stream's `usage.cost` remains "the total amount charged to your account" (COST_PROXY.md section 2) — under BYOK this should carry the 5% fee (or zero within the allowance). What it shows for BYOK requests exactly is **unconfirmed** (no paid call allowed); DEEPINFRA.md documents that the DeepInfra endpoint prices equal the discounted DeepInfra direct prices, so the OpenRouter-side `cost` plus DeepInfra's own numbers can be cross-checked on the first real run.
  2. `GET /api/v1/key` now returns `byok_usage`, `byok_usage_daily/weekly/monthly`, and `include_byok_in_limit` (https://openrouter.ai/docs/api_reference/limits) — per-key BYOK usage on the OpenRouter side, the same delta measurement oc-sub already uses (KEY_SOURCE.md).
  3. DeepInfra `GET /payment/usage/{api_token}` gives the raw DeepInfra spend for that key (DEEPINFRA.md section 4) — independent of OpenRouter and free.

**Unconfirmed:** whether `usage.cost` in a BYOK stream includes the 5% fee, whether it reports the upstream DeepInfra charge, and whether OpenRouter's fp4 DeepInfra endpoint (the precision risk of DEEPINFRA.md) is identical to what BYOK hits — BYOK routes to the same DeepInfra endpoints, so the fp4 problem carries over unchanged.

## 3. A host-side forwarder through `host.docker.internal`

- The sandbox **can** reach the host: SANDBOX.md section 7, problem 4 — "`curl http://host.docker.internal:8767` from inside reached the host `opencode serve`... `sbx policy check` allows it under the current global policy." The default global policy of `sbx` is `default-allow-all` (SANDBOX.md problem 3).
- The oc-sub code deliberately closes this: `NETWORK_DENY_HOSTS` denies `host.docker.internal`, `localhost`, `127.0.0.0/8`, and the private ranges (src/sandbox.ts:39–46), `up` applies `sbx policy deny network --sandbox NAME` for them (src/sandbox.ts:1097–1099), and it verifies the denial on every start (src/sandbox.ts:1191–1197). The comment explains the subtlety: "`sbx` rewrites `host.docker.internal` to `localhost`, so a deny rule for `host.docker.internal` alone is not enough" (src/sandbox.ts:36–37).
- The `sbx` docs say nothing about a host-side credential proxy pattern; the documented credential mechanism is exactly the host-side proxy with sentinel values (question 1). The kits page warns against moving traffic off the built-in forward proxy: setting proxy variables in a kit "points traffic away from the forward proxy, so it can no longer apply network policy or inject credentials, and those requests typically fail to connect" (https://docs.docker.com/ai/sandboxes/customize/kits).
- COST_PROXY.md section 1 already judged the same idea for openrouter: "A proxy on the host is not reachable: the sandbox policy denies `host.docker.internal`... Opening a hole to the host would undo the step 9 boundary."

So option C works mechanically only by weakening the deny list, fails K5, and adds a second proxy process to own. The `sbx` proxy is already that forwarder, per domain, with the key on the host.

## 4. Options judged

| Criterion | A: `sbx secret set-custom` (or custom kit) for `api.deepinfra.com` | B: OpenRouter BYOK (DeepInfra key in OpenRouter) | C: host-side forwarder on `host.docker.internal` |
|---|---|---|---|
| K1 key safety | Pass: real key only on host, placeholder in sandbox (docs, §1) | Pass: key on OpenRouter, sandbox keeps openrouter placeholder | Pass technically, but only reachable by weakening the deny list (K5) |
| K2 effort | Low: one `sbx` call + placeholder file in `up`, mirrors openrouter path; verify flag names | Lowest: OpenRouter settings only; optional one-time BYOK create via management API to pin `allowed_api_key_hashes` | Medium: new host process, lifecycle, port, plus policy changes |
| K3 cost truth | Best: DeepInfra `usage.estimated_cost` per request (via existing cost proxy), `GET /payment/usage/{api_token}` per key; no fee noise | Good: stream `usage.cost` (fee semantics unconfirmed), `byok_usage` per OpenRouter key, DeepInfra usage API; small 5% fee noise outside allowance | Same as A for the data path |
| K4 limits/hops | Direct to DeepInfra: DeepInfra's own limits, one hop, no OpenRouter fee | One extra hop, 5% fee above allowance, BYOK-priority routing quirks, fp4 endpoint unchanged | Direct, but an extra process in the path |
| K5 structural fit | Pass: uses the documented sbx mechanism | Pass: nothing changes in the sandbox | **Fails**: reopens the hole src/sandbox.ts closes |
| Known failure modes | `set-custom`/kit version mismatch in 0.45.1 (unconfirmed); placeholder must actually appear in the request; kit path needs a binding for third-party v2 kits | 5% fee on OpenRouter list price above $25k/month allowance; BYOK overrides provider ordering (docs); fp4 precision risk carries over; BYOK is workspace-wide unless pinned by key hash | Deny-list erosion; agent inside sandbox reaches other host services; second proxy to babysit |

**Recommendation: option A.** K1, K2, and K5 decide it: the same pattern oc-sub already ships for openrouter, one small extension of `up` in src/sandbox.ts, the key stays host-side by the documented mechanism, and no hole in the sandbox boundary. Prerequisite: the main thread confirms `sbx secret set-custom --help` exists in the installed 0.45.1 (the brief forbade that check here). If it does not exist, option B is the fallback and needs only OpenRouter settings — pin it with `allowed_api_key_hashes` and `is_byok_only` so the project's OpenRouter key is the only consumer. Note that both A and B leave the fp4 precision risk of DEEPINFRA.md unresolved; that risk is independent of the key path and is judged there.
